> 依据鹏哥 C 语言进阶第 22 章整理。命令示例使用 GCC，MSVC、Clang 的选项和生成格式可能不同，但主要概念相通。

## 1. 引入：有声明为什么还报找不到函数

```c
int add(int a, int b);
```

这行声明只让编译器知道如何检查调用，并没有提供函数体。源文件可能编译成功，最终链接却找不到 add 的定义。理解各阶段职责，才能判断该补头文件，还是该把实现文件加入构建。

可以把常见工具链看成：

```text
main.c --预处理--> main.i --编译--> main.s --汇编--> main.o
math_utils.c -------------------------------> math_utils.o
main.o + math_utils.o + 库 --链接--> 可执行程序
```

这是便于观察的逻辑阶段。编译器可以在内部合并步骤，不要求每次普通构建都留下 `.i` 和 `.s` 文件；语言规定的翻译阶段与具体工具命令也不是严格一一对应。

## 2. 准备一个完整三文件工程

分别保存下列内容。

### math_utils.h：共享接口

```c
#ifndef MATH_UTILS_H
#define MATH_UTILS_H

extern int calculation_count;
int add(int a, int b);

#endif
```

### math_utils.c：定义对象和行为

```c
#include "math_utils.h"

int calculation_count = 0;

int add(int a, int b)
{
    ++calculation_count;
    return a + b;
}
```

### main.c：调用接口

```c
#include <stdio.h>
#include "math_utils.h"

int main(void)
{
    int result = add(10, 20);
    printf("result=%d count=%d\n", result, calculation_count);
    return 0;
}
```

本例只做一次小整数计算，结果为 `result=30 count=1`。不要把有状态函数调用和状态读取放在同一个 printf 的不同实参中，再假定它们固定先后执行。

## 3. 第一步：预处理

```sh
gcc -std=c17 -E main.c -o main.i
```

`-E` 让 GCC 在预处理后停止。主要动作包括：展开头文件、替换宏、选择条件编译分支、移除注释并保留必要的源位置记录。

预处理器不会看到 `int x = 1;` 就实际为程序分配运行内存，也不会执行 main。它处理的是记号和指令，宏展开不等于函数调用。

打开 main.i，能看到 math_utils.h 的声明已进入当前翻译单元，而 add 的函数体仍在另一个源文件中。系统头文件也被展开，所以预处理结果可能比原始文件长很多。

宏不符合预期、include 路径找错、某段代码被条件编译移除时，先查看 `.i`，比在原代码里盲猜更直接。

## 4. 第二步：编译到汇编

```sh
gcc -std=c17 -S main.i -o main.s
```

编译器进行词法、语法、语义分析，再生成中间表示、优化和目标相关代码。用表达式 `array[index] = (index + 4) * (2 + 6);` 观察：

- 词法：分出标识符、常量、括号和操作符等记号。
- 语法：按规则构建表达式结构，确认乘法、加法与赋值如何组合。
- 语义：检查 array、index 的声明、操作是否合法、是否需要转换。
- 优化：例如把常量 `2 + 6` 提前折叠为 8。

优化必须遵守语言的可观察行为约束，但对已经触发未定义行为的程序不需要维持某次“看上去正常”的结果。所以不能把优化后不同表现一概归为编译器错误。

汇编是特定指令集的文本表示，不是所有平台通用的 C 替代品。即使源代码相同，不同架构和优化等级的汇编也可能很不同。

## 5. 第三步：生成目标文件

```sh
gcc -c main.s -o main.o
gcc -std=c17 -Wall -Wextra -c math_utils.c -o math_utils.o
```

第二条命令直接从 C 生成目标文件，相当于完成前几个步骤。目标文件包含机器代码、数据、符号表、重定位信息等，通常还不是能独立运行的最终程序。

main.o 知道它引用 add 和 calculation_count，但还没有在单独编译时得到最终地址。math_utils.o 则提供这些名称对应的定义。

在相应工具链可用时，可观察：

```sh
nm main.o
nm math_utils.o
objdump -r main.o
```

nm 常用 U 表示尚待解析的引用，T/D/B 等表示代码或不同数据段中的定义；精确符号名和类别受格式、平台和编译器影响。objdump 的重定位信息显示哪些位置还需要链接时修正。

## 6. 第四步：链接

```sh
gcc main.o math_utils.o -o demo
```

链接器收集各目标文件与库的定义，解析符号，为代码和数据安排位置，并应用必要重定位。缺少某个实现、重复提供不允许重复的定义、目标架构不匹配，都会在此阶段暴露。

运行 Windows 下的 `demo.exe`，或类 Unix 下的 `./demo`，应输出预期结果。`.o`、`.obj` 只是常见后缀，实际 ELF、COFF 等格式由目标平台与工具链决定。

| 错误 | 常见原因 | 处理方向 |
| --- | --- | --- |
| 头文件找不到 | include 路径或名称错误 | 检查路径与 `-I` |
| 未声明/类型冲突 | 缺正确声明或声明不一致 | 统一共享头文件 |
| undefined reference | 没有链接实现或库 | 加入对应 `.o`、`.c`、库 |
| multiple definition | 多处定义同一外部对象/函数 | 保留一个定义，其他用声明 |
| format/architecture 错误 | 混用不兼容目标文件 | 统一目标架构和构建配置 |

声明存在不等于定义存在。链接器通常也不做完整 C 类型一致性检查，跨文件各自写错原型可能仍链接成功，因此必须共享同一个头文件，并让定义文件也包含它。

## 7. static、extern 与头文件保护的边界

`extern int calculation_count;` 通常是声明；`int calculation_count = 0;` 是定义。把后者直接放进被多个 `.c` 包含的头文件，会在每个翻译单元产生定义。

头文件保护只防同一翻译单元内重复展开，不会合并不同 `.c` 的外部定义。文件作用域 `static` 则建立内部链接，各文件中的同名对象互相独立，也不能用它伪装一个本应共享的全局对象。

头文件中适合放类型、宏、函数声明、extern 对象声明；小型 `static inline` 函数可以作为专门设计的例外。通常不要 `#include "math_utils.c"`，应让源文件各自参与构建。

## 8. 静态链接与动态链接的直观区别

静态库通常是目标文件的集合，链接时按规则选择需要的内容加入最终程序；动态库提供的代码可能在装载时或运行时与程序连接。静态并不意味着“整个库全部复制”，动态也不等于“永远不占内存”。

构建成功后仍可能因动态库缺失、版本不匹配或搜索路径问题无法启动，这属于装载/运行环境，不应通过修改 C 语法解决。调用约定、结构体布局和目标架构共同影响二进制兼容性。

## 9. 程序如何开始和结束

常见宿主系统先装载可执行文件及依赖，运行时完成必要初始化，再调用 main。自动对象、静态对象和动态分配对象按各自存储期存在；实际栈帧、寄存器和内存段是实现层面的安排。

main 正常返回或调用 exit 会走正常终止流程，包括刷新和关闭标准流等处理；异常终止不保证同样清理。嵌入式等独立环境的入口、装载方式和运行支持可以不同，不能把桌面启动流程视为全部 C 平台的唯一模式。

## 10. 动手实验

依次执行四阶段命令；故意漏掉 math_utils.o，识别链接失败；把 add 声明改错，观察定义文件包含共享头文件后的编译诊断；为 math_utils.c 加一个 static 内部函数，再观察符号表。

阶段化排错的原则是：先确认错误在哪一步，再补该步骤需要的信息。不要用“重装 IDE”代替检查缺失的实现文件，也不要用强制转换掩盖接口不一致。
