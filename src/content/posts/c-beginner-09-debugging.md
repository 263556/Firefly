## 1. 引入：能运行不等于算对

要求计算 `1! + 2! + 3!`，预期是 `1 + 2 + 6 = 9`。下面是一个有逻辑错误的例子：

```c
int sum = 0;
int factorial = 1;
for (int n = 1; n <= 3; ++n) {
    for (int i = 1; i <= n; ++i) {
        factorial *= i;
    }
    sum += factorial;
}
printf("%d\n", sum); // 错误地得到 15
```

编译器不一定能知道你的数学意图。调试要先写预期，再观察状态在哪一步偏离预期，而不是不断改代码碰运气。

## 2. 调试的基本流程

1. **复现**：记录输入、实际结果、预期结果、构建配置。
2. **缩小**：用尽可能小的输入重现，如把 10 项减成 3 项。
3. **定位**：断点停在可疑位置，观察每次迭代的状态。
4. **解释**：找到错误发生原因，而不只是某个“奇怪的值”。
5. **修复并回归**：重新测试原输入、最小输入和边界输入。

错误大致分为：编译错误（语法、类型等）、链接错误（缺少或重复定义）、运行错误（崩溃等）、逻辑错误（结果不符）。先判断阶段，有助于选择工具。

## 3. Debug 与 Release

Debug 配置通常带调试信息、优化较少，源码和执行过程比较容易对应；Release 通常启用优化，变量可能被消除、重排或保存在寄存器中。具体选项取决于工程配置，并非语言保证“Debug 永不优化”或“Release 必定更小”。

程序若只在某个配置下出问题，优先检查越界、未初始化变量、对象生命周期等问题，不要简单归因于编译器。未定义行为可能在不同优化级别呈现完全不同的结果。

## 4. 常用操作与窗口

| 操作 | Visual Studio 常见快捷键 | 用途 |
| --- | --- | --- |
| 切换断点 | F9 | 在目标行前暂停 |
| 开始或继续 | F5 | 运行到下一个断点或结束 |
| 逐过程 | F10 | 通常把一次函数调用作为一步 |
| 逐语句 | F11 | 需要时进入函数内部 |
| 跳出函数 | Shift+F11 | 执行完当前函数回到调用者 |
| 不调试运行 | Ctrl+F5 | 直接执行，不进入断点调试流程 |

**监视窗口**：查看 `n`、`i`、`factorial`、`sum` 等表达式。尽量监视无副作用表达式，避免在观察时调用会修改状态的函数。

**局部变量/自动窗口**：快速查看当前函数的上下文。**调用堆栈**：查看如何进入当前函数，递归中尤其有用。**内存窗口**：通过地址观察字节内容，辅助理解数组和指针，但必须结合类型解释这些字节。

## 5. 案例推演：阶乘变量没有重置

在 `sum += factorial` 行打断点，每轮停下后记录：

| n | 本轮开始的 factorial | 内层结束值 | sum 更新后 |
| --- | --- | --- | --- |
| 1 | 1 | 1 | 1 |
| 2 | 1 | 2 | 3 |
| 3 | 2 | 12 | 15 |

第三轮应从 1 重新求 `3!`，实际却从上一轮的 2 开始。修复方案一：把 `int factorial = 1;` 移入外层循环，每轮重新计算。

更好的方案二：利用 `n! = (n - 1)! * n`，不必每次从头算。

```c
#include <stdio.h>

int main(void)
{
    long long factorial = 1;
    long long sum = 0;
    for (int n = 1; n <= 10; ++n) {
        factorial *= n;
        sum += factorial;
    }
    printf("%lld\n", sum); // 4037913
    return 0;
}
```

第一种是 O(n²) 的重复计算，第二种为 O(n)。限制在 10 是为了示例范围；输入继续增大仍需检查乘法和累加是否溢出，换成 `long long` 也不是无限精度。

## 6. 数组越界：不要把偶然布局当规律

```c
// 错误示例：a[10] 不存在。
int a[10] = {0};
for (int i = 0; i <= 10; ++i) {
    a[i] = 0;
}
```

正确条件是 `i < 10`。越界写可能破坏其他变量、造成崩溃，甚至暂时看不出异常。课件展示了特定环境下越界覆盖循环变量导致死循环的现象，但这不是 C 的固定行为；x86/x64、Debug/Release 都不保证某种相对局部变量布局。

可设置条件断点 `i == 10`，在第一次非法写入之前停下。注意调试器高亮的行通常是接下来要执行的行，观察值时要区分“本句之前”和“本句之后”。

GCC/Clang 环境可启用 `-Wall -Wextra`，并在支持时使用 AddressSanitizer、UndefinedBehaviorSanitizer，例如 `-g -fsanitize=address,undefined`。这些工具能发现部分问题，不能代替正确的边界设计。

## 7. 对扫雷进行有目标的调试

先固定种子或手工棋盘，再在布雷、邻雷统计、翻格三个位置分别设断点。检查 `placed` 是否等于实际雷数、邻居坐标是否落在缓冲区、重复点击时 `opened` 是否不变。

多次循环只关心某格时，可设置条件断点 `row == 1 && col == 1`。错误写入者难定位时，工具支持的数据断点能在特定内存被修改时暂停；其可用性依赖调试器和目标环境。

## 8. 日志与 AI 辅助

难以暂停的程序可记录关键输入、状态迁移和错误码。日志要能重建执行路径，避免淹没在无意义输出里。向 AI 求助时提供最小复现、编译器版本、实际与预期结果，不要只贴一句“报错了”。得到建议后仍需亲自单步和回归验证。

练习：给求数组最大值程序制造一个边界错误，先写出预期，再用断点定位第一次错误访问；修复后测试单元素和全负数数组。
